> **第一部分**是已经自动化、可直接跑的真实测试（含真实浏览器 E2E）；

## 零、环境准备

```powershell
# 1) git 与 cargo 不在默认 PATH 上（DSH 运行时的 PATH 被裁剪过），需要手动前置：
$env:PATH = "$env:USERPROFILE\.cargo\bin;C:\Program Files\Git\cmd;$env:PATH"

# 2) 安装依赖（首次或依赖变更后）
corepack pnpm install

# 3) 构建前端产物（E2E 依赖它）
corepack pnpm --filter @javis/desktop build

# 4) 启动桌面应用做手工测试
corepack pnpm dev
```

**E2E 用的浏览器**：默认使用本机已有的 chromium headless shell：

```
C:\Users\s1897\AppData\Local\ms-playwright\chromium_headless_shell-1208\chrome-headless-shell-win64\chrome-headless-shell.exe
```

换机器/换路径时用环境变量指定，不必改代码：

```powershell
$env:JAVIS_E2E_CHROMIUM = "D:\path\to\chrome-headless-shell.exe"
```

**注意（真实踩过的坑）**：PowerShell 控制台会把中文输出显示成乱码，但**文件内容是正确的**。
所以怀疑输出时，把结果写进文件再用编辑器看，不要以控制台显示为准。

# 第一部分：已自动化的真实测试

## 用例 A1 —— 真实浏览器端到端冒烟（`pnpm e2e:smoke`）

**这是最重要的一条**：本仓库其余所有测试都跑在 jsdom 里，**从不加载生产 bundle**。
这条用例用**真 chromium 加载构建产物**，因此能抓到"单测全绿但应用起不来"的问题。

> 它已经抓到过一次真实回归：一次 chunk 拆分让全部约 2,900 个单测通过，
> 而构建产物在真实浏览器里挂载失败（`Cannot read properties of undefined (reading 'PureComponent')`），
> 屏幕上只剩"正在启动…"。**修好后才有这条用例。**

**前置**：已执行 `corepack pnpm --filter @javis/desktop build`（产物在 `apps/desktop/dist`）。

**执行**：

```powershell
corepack pnpm e2e:smoke
```

**断言（4 条，任一不满足即失败并退出码非零）**：

| # | 断言 | 判定依据 |
|---|---|---|
| 1 | 应用**挂载**了 | `#root` 渲染的 HTML 字符数 ≥ 1000（可用 `--min-root-chars` 调整） |
| 2 | **3 个工作台地标**都在 | 正文包含 `新建对话`、`设置`、`聊点什么` |
| 3 | 应用**可交互** | 点击输入框后它真的获得焦点（`document.activeElement`） |
| 4 | **无真实错误** | 非 Tauri 的 console error / page error 均为 0 |

**为什么第 2、3 条必要**：只断言"有 HTML"会因为一个渲染到一半的空壳而通过。
地标是工作台外壳的不同部位；交互断言能抓到"渲染了但事件没挂上"。

**Tauri 相关失败单独计数**（`tauri-related=`）：纯浏览器里 `invoke` 必然缺失，
把它们和真实崩溃混在一起会让真实崩溃淹没在预期噪声里。

**通过时的样子**：

```
e2e: rendered=true rootHtmlChars=9184 title="Javis"
e2e: landmarks 3/3  interactive=true
e2e: console errors=0 page errors=0 failed requests=0 tauri-related=0
e2e: the built front-end mounts and renders with no errors.
```

**产物**（失败时用来定位）：

| 文件 | 内容 |
|---|---|
| `.dsh-tmp/e2e-report.json` | 完整报告：错误原文、地标命中情况、`interactive`、耗时 |
| `.dsh-tmp/e2e-smoke.png` | 截图（直接打开看界面长什么样） |

**故障注入（验证这条用例不是摆设）**：

```powershell
node scripts/e2e/smoke.mjs --min-root-chars 100000
# 期望：rendered=false 且退出码 1
```

## M1 —— 首次运行引导（对应 `E1` / `E1b`）

**目标**：确认"缺什么、下一步做什么"的诊断结果与真实配置一致。

**核心逻辑**：`packages/core/src/setup-diagnostics.ts`（11 个单测已通过）

**步骤**：

1. **清空模型配置**（或新装环境）：设置里删掉服务商/模型/API 密钥。
2. 重启应用，观察失败信息。
3. 依次填：服务商 → 模型 → API 密钥，每填一步看提示是否更新。
4. 把工作区留空，观察是否**只提醒不阻断**（应能聊天）。
5. 用一个**未知服务商名**（如 `mystery`），看是否给"仅当兼容 OpenAI 接口才可用"的警告。

**期望**：

| 检查点 | 期望 |
|---|---|
| 缺服务商/模型/密钥 | 阻断，且明确指向**下一步该做哪一个** |
| 缺工作区 | **仅提醒**（聊天可用），不阻断 |
| 无需密钥的本地服务商 | 不应要求填密钥 |
| 未知服务商 | 警告但不阻断 |

**当前状态**：诊断核心有测试；**引导 UI 未接线（`E1b`）**——所以很可能看到的是零散提示而非统一清单。**记录你看到的实际形态。**

## M2 —— 失败信息带"下一步按钮"（对应 `E2` / `E2c` / `E2d` / `E2d-ui`）

**目标**：任务失败时，是否给出**可点的下一步动作**（重试 / 检查密钥 / 打开设置 / 查看日志）。

**核心逻辑**：`failure-guidance.ts`（14 类失败）、`failure-actions.ts`（按钮描述符）、`apps/desktop/src/failure-action-view.ts`（app 侧适配）

**步骤**（逐个触发，每次记录看到的文案与按钮）：

| # | 触发方式 | 期望归类 | 期望动作 |
|---|---|---|---|
| 1 | 把 API 密钥改错再发一条 | `auth` | 检查 API 密钥 / 打开设置 / 重试 |
| 2 | 把模型名改错 | `model_unconfigured` 或 `auth` | 打开设置 |
| 3 | 断网后发一条 | `network` | 重试 / 打开设置 |
| 4 | 发一个超长目标（超上下文） | `context_overflow` | **缩短输入** / 换模型 |
| 5 | 让模型只输出思考过程（难构造，可跳过） | `empty_final_content` | 重试 / 换模型 / 看日志 |
| 6 | 正常任务中途取消 | `cancelled` | 重试 |

**特别检查**：

- 失败文案是否**说出了原因和做法**（而不是泛泛的"模型请求失败"）；
- 是否出现**可点的按钮**；
- 没有原始目标时，"重试"是否**禁用并说明**（而不是重开空输入框）；
- 审批被拒绝后，是否**不提供"补救"按钮**（用户已经做决定了）。

**当前状态**：分类与动作**已接线到任务快照**（`TaskSnapshot.failureGuidance`），
**但 UI 渲染按钮未接线（`E2d-ui-组件`）**。所以最可能的现象是：
**文案已经变好、但看不到按钮**。请确认这一点并在报告里注明。

## M3 —— 统一审批中心与"本次会话不再询问"（对应 `D5` / `D5b`）

**目标**：审批是否集中、是否按风险分级、会话授权是否**永不覆盖危险操作**。

**核心逻辑**：`packages/core/src/approval-center.ts`（17 个单测）

**步骤**：

1. 触发一次**普通文件写入**审批 → 记录卡片是否显示**风险等级**与**理由**。
2. 在同一会话内选择"本次会话不再询问" → 再触发同类写入 → 期望**不再弹窗**。
3. 触发一次**不可逆/逃出工作区**的操作（如把路径写到工作区外 `../../`）→ 期望风险等级为**危险**。
4. 对第 3 步的操作尝试"不再询问" → **期望被拒绝**，并提示必须每次审批。
5. 同时触发**两个不同来源**的审批（如文件写入 + git 提交）→ 观察是否进**同一个队列**。

**期望**：

| 检查点 | 期望 |
|---|---|
| 风险分级 | safe / risky / dangerous，**并给出理由** |
| 会话授权 | 生效，且有 TTL 与撤销 |
| 危险操作 | **永不进入会话授权** |
| 多来源 | 归一化进一个队列（而非散在各面板） |

**当前状态**：核心有测试；**未投递进真实审批流（`D5b`）**。预期现象：审批仍是分散的旧形态。

## M11 —— `.javis` 配置：禁用一个工具（对应 `B3`，**已接线，应能验证**）

**这条是本清单里**最可能已经可用**的一条**（`disabled` 已真正接线）。

**步骤**：

1. 在工作区根目录创建 `.javis/config.json`：

```json
{
  "tools": [
    { "name": "file.scanMarkdownDocuments", "disabled": true }
  ]
}
```

2. 重启应用（或触发配置重载）。
3. 让任务尝试使用该工具，或查看可用工具列表 → 期望**该工具已消失**。
4. 再试**放宽权限**（把某个 `confirmed_write` 工具声明成 `read`）→ 期望**被拒绝**并在日志里看到
   "配置层只能收紧权限，绝不能放宽"。

**为什么值得优先做这条**：它验证的是"配置文件能真正改变运行时行为"这条链路，
一旦通了，其余配置类能力（hook / agent 声明 / SKILL）的接线就都是同一条路。
